# NMK16 MiSTerFPGA Core — Project Plan

## Context

`Arcade-NMK16_MiSTer` currently contains only a MAME source checkout (`mame/src/mame/nmk/nmk16.cpp`, `nmk16_v.cpp`, `nmk16spr.cpp/h`, `nmk214.cpp/h`, `nmk_irq.cpp/h`, `nmk004.cpp/h`) used purely as the behavioral reference. The goal is to turn this into a real MiSTerFPGA arcade core project — Verilog/SystemVerilog RTL, Quartus 17.x build, `.rbf` bitstreams and `.mra` ROM-definition files — that fully supports every `GAME()`/`GAMEL()` entry in `nmk16.cpp` (85 romsets across roughly a dozen distinct hardware sub-families spanning NMK, UPL, Tecmo, Atlus, Comad, and Afega boards, 1989–1997).

Research against the MAME source (full read of all six files above) surfaced the two facts that most shape this plan:

1. **NMK004** is not custom silicon — it's a Toshiba **TLCS-90** microcontroller (TMP90C840AF) running a fixed 8KB boot ROM plus a per-game external program (up to 56KB). The *same* TLCS-90 family is reused as the protection MCU (NMK-110/113/215) on several other boards. **No open-source TLCS-90 FPGA core exists** (confirmed by web search) — this is a from-scratch CPU core, and it gates roughly half the game list.
2. Several boards' protection is only known to MAME as a **C++ behavioral simulation** of undumped or unverified silicon (shared-RAM handshakes, NMK214 graphics-descrambler init sequences) — there is no ground truth beyond "match what MAME does."

Given that, and per the project owner's answers to the clarifying questions asked before this plan was approved: the plan builds **one `.rbf` per distinct hardware family** (not per romset) with a `.mra` per game, adopts a **simulation + MAME-oracle verification methodology** (tracing MAME's CPU bus/video output and diffing against RTL in simulation before hardware bring-up — the approach used by the closest analogous project, Kaneko16-MiSTer), includes **hardware bring-up checkpoints** per tier (a DE10-Nano and test ROMs are available), and sequences delivery by **increasing hardware complexity** with no fixed priority game.

## Reference architecture (from MiSTer-devel / jotego ecosystem research)

Surveyed several existing MiSTer arcade cores of comparable scope to avoid reinventing conventions:

- **Arcade-Darius_MiSTer**, **Arcade-SkySmasher_MiSTer**, **Arcade-HeatedBarrel_MiSTer** — standard layout: `rtl/<game>/` custom logic, `rtl/fx68k/` (68000), `rtl/t80/` (Z80), `rtl/jt12/` (YM2203/OPN family) or `rtl/jtopl2/` (YM3812), `rtl/jt6295/` (OKIM6295), `sys/` (MiSTer framework), top-level `<Core>.qpf/.qsf`, `Template.sv/.sdc`, `files.qip`. Built with **Quartus Prime Lite 17.0.x** for Cyclone V `5CSEBA6U23I7` (the DE10-Nano part) — matches the requested target exactly.
- **kaneko16-mister** (alphanu1) — the closest analog in spirit: one core family supporting many games via custom `VIEW2-CHIP` tilemap and `VU-002/KC-002` sprite chips, explicitly *"not an emulator: RTL that behaves as the original silicon did, verified against MAME as an oracle,"* with fuzzed/oracle-diffed testbenches, a tiered game-support roadmap by protection-MCU complexity, and vendored third-party cores fetched by a bootstrap script rather than committed. This project's structure and methodology are the template for NMK16.
- Reusable components to vendor (git submodule or pinned bootstrap-fetch, not hand-copied): **fx68k** (68000), **T80** (Z80), **jt12** (YM2203/OPN), **jtopl2** (YM3812/OPL2), **jt6295** (OKIM6295), MiSTer-devel **sys/** framework, Sorgelig's standard `sdram.sv` controller. All match the exact chips originally named for reuse.

## Custom RTL components required

1. **TLCS-90 CPU softcore** — from scratch, referenced against MAME's `cpu/tlcs90/tlcs90.cpp`. Single biggest new-CPU-core effort in the project; built once, reused for both the NMK004 sound-MCU role and the NMK-110/113/215 protection-MCU role (different peripheral wiring, same core).
2. **NMK004 device wrapper** — latch/IRQ glue per the exact register map found (`0xf800/f900/fa00` chip relays, `0xfb00/0xfc00` host latches, `0xfc01/fc02` OKI bank select, NMI-driven handshake with `synchronize()` semantics in MAME — must be replicated as real bus handshake timing, not a software shortcut).
3. **`nmk16spr` sprite engine** — 256-slot sprite RAM, variable W×H (1–16 tiles), per-game flip/color-width callback behavior (4/5/6-bit color, powerins' inverted flip-bit mapping), and critically the **per-frame sprite-fetch clock budget** (`m_max_sprite_clock`) that causes real hardware to silently drop late sprites — must be modeled as a structural per-line/per-frame fetch-bandwidth limit, not a software counter, or several games will show sprites MAME itself doesn't render. Reverse-order priority compositing against the tilemap priority bitmap.
4. **Tilemap engine(s)** — must support the family's several layer configurations (1–3 BG/TX layers, 16×16/8×8 tiles, page-mapped vs flat addressing, the hi-res-only tilemap wraparound quirk, and the gunnail/raphero true per-scanline raster X+Y scroll, which is the hardest video item identified).
5. **`nmk214` descrambler** — stateless, table-driven address/data bit-permutation network; straightforward combinational Verilog once the per-game bitswap tables (already present in the MAME source) are extracted.
6. **`nmk_irq` timing generator** — dual-PROM-driven scanline state machine (V-PROM drives IRQ1–4 + sprite-DMA-trigger edges; H-timing is *not* accurately emulated by MAME itself, so the three fixed pixel-clock/htotal tables recovered from the source are the ground truth to implement directly as fixed counters per resolution class). V-PROM content is per-game and must be loaded as an initialized ROM, not hardcoded.
7. **Afega video/scroll variant** — separate-but-related tilemap/scroll/flip logic and an 8bpp tilemap mode (grdnstrm), reusing the sprite/CPU/sound infrastructure from earlier tiers.
8. **NMK112 OKI bank/sample-rate controller** — small, standalone MAME device (`devices/machine/nmk112.cpp`), read in full (see Resolved Items below) — trivial FPGA target, reused across nearly every family.

Chips reused as-is from existing MiSTer/jotego cores: 68000 (fx68k), Z80 (T80), YM2203 (jt12), YM3812 (jtopl2), OKIM6295 (jt6295) — no custom work needed beyond standard integration glue.

## Verification methodology

- **Simulation harness** (Verilator or equivalent) for every custom RTL block, driven by traces extracted from MAME itself (a debug/Lua-scripted MAME build dumping CPU bus cycles, video frame buffers, and sprite-list contents cycle-by-cycle) — diff RTL simulation output against the MAME oracle before synthesis.
- **TLCS-90 core validated first in isolation** against MAME's `tlcs90.cpp` execution trace on the fixed NMK004 boot ROM + a representative external program, independent of the rest of the system, since it's the highest-risk new component.
- **Frame-level oracle diffing** for video output once the pipeline is assembled per tier.
- **Hardware bring-up checkpoint at the end of each tier** — flash, play, compare against MAME output/video capture, before moving to the next tier.

## Delivery plan (tiers, by increasing hardware complexity)

- **Tier 0 — Infrastructure** (prerequisite for everything): repo scaffold (`rtl/`, `sys/`, `sim/`, `releases/`, `tools/`, `docs/` — created), vendor/pin fx68k, T80, jt12, jtopl2, jt6295, MiSTer `sys/` framework and `sdram.sv` (bootstrap script + lock file, not committed copies), Quartus 17.0.x project skeleton for `5CSEBA6U23I7` (`Template.sv/.sdc`, `.qpf/.qsf`, `files.qip`), MAME-trace generation tooling for the oracle harness, license-compliance check per vendored component, and the **Milestone 0 per-game hardware inventory table** (all 85 entries → family/tier/quirks). `.mra` authoring workflow decided (hand-authored per-family template + light generation script, given MAME's `ROM_START` regions map fairly mechanically to `romstruct`).
- **Tier 1 — Family A** (cactus, bjtwinp, nouryokup — the three genuinely unprotected/unencrypted romsets on the bjtwin hardware, not the whole bjtwin/sabotenb/nouryoku group): proves out fx68k integration, `nmk16spr`, single-layer tilemap engine, `nmk_irq`, `nmk112`, palette, jt6295×2. No new CPU core needed yet — cheapest path to a first playable, oracle-verified game. Smaller tier than originally scoped; most of this hardware family actually requires the TLCS-90 protection MCU (moved to Tier 4).
  **In progress — see `docs/tier1-bjtwin.md` for full detail.** CPU + memory-map + interrupt subsystem (`rtl/bjtwin/bjtwin_core.sv`, `nmk_irq_hacky.sv`) is built and verified: real `cactus` ROM execution in Verilator matched **all 1617 events** of a captured MAME oracle trace exactly (address/data/mask), with a constant +57-cycle startup offset across every single event. Video pipeline (`video_bjtwin.sv`: tile decode, `nmk16spr`-style sprite decode/compositing, palette RGB decode, procedural per-frame renderer) is built and running; every component formula is independently verified bit-exact against MAME source (palette decode, tile pixel bit-ordering — including catching and correcting a wrong initial assumption about plane-to-bit significance — COL-scan addressing, ROM extraction CRC), and an end-to-end sanity check confirms the pipeline is internally self-consistent (RTL-rendered pixels match a hand-computed expected value derived from the verified formulas, byte-exact). Full-frame CRC32 does not match the MAME oracle, but this is now conclusively closed out via a *state* comparison instead of a *pixel* comparison (`sim/compare/state_diff.py`, replaying bus-write traces into memory images and diffing directly — valid regardless of frame-timing alignment): palette RAM matches MAME's oracle **1024/1024 addresses exactly**, and tilemap VRAM matches **1706/1706** of what the (Lua-tap-overhead-limited) oracle capture covers, zero mismatches in both. Combined with the source-verified decode formulas, the data path is proven correct — the frame-CRC mismatch is confirmed to be the render FSM's phase-alignment gap, not a content bug. Along the way, ruled out three plausible divergence causes (stubbed OKI ports, DSW/input defaults, the `mainram_strange_w` quirk — none apply) and discovered that MAME's sprite-DMA (`sprite_dma()`) is a host-memory copy invisible to CPU bus tracing, meaning sprite-buffer verification will need a different method later. **Sprite rendering verification (in progress)**: a PC-tracing tool (piggybacking on fx68k's function-code lines, since it has no direct PC pin) proved main-line code matches MAME almost exactly through 15 frames — including leaving a shared wait loop at exactly the same frame. Bus-tap-based investigation then *appeared* to show a real CPU control-flow bug (a mainram POST-test sweep loop not stopping where MAME's did), which was written up as confirmed and a fix was attempted — but this was **retracted**: MAME's own debugger (instruction trace + a `wpset` watchpoint), cross-validated against a case the Lua tap got right, proved the loop actually runs its full correct course in real MAME too, and the earlier "zero writes" bus-tap results were a false negative — a real, reproducible blind spot in MAME's Lua `install_write_tap` mechanism for at least part of the mainram region, not a CPU bug. The RTL's behavior is very likely correct; sprite verification is **not** blocked after all. Lesson banked for future oracle captures: cross-check surprising "zero events" bus-tap results against a debugger watchpoint (`wpset` + `-debug -debuglog`) before trusting them. That lesson was then built into real, reusable tooling (`sim/oracle/debug_capture.py`, generates a `.debugscript` with an auto-continuing watchpoint action and parses `debug.log` into the same nmktrace grammar the Lua tap uses) and run for real: **sprite RAM now matches 2048/2048 addresses exactly** (complete coverage, not just the 5 manually-inspected events from the retraction), tilemap VRAM's earlier partial 1706/2048 coverage is now a **complete 2048/2048 match**, and a bonus full-mainram sweep matched 32,729/32,763 (99.9%, the residual fully explained as a capture-length artifact around the stack region, not a divergence). Kept one independently-real bug fix found along the way (`DTACKn` was asserting during interrupt-acknowledge cycles alongside `VPAn`, risking a bogus autovector read). **`sprite_dma()`'s output buffer is now verified too**: MAME's `m_spriteram_old` (the actual DMA'd sprite draw buffer, a host-memory C++ copy invisible to both the Lua bus tap and `debug_capture.py`'s watchpoints) was read directly via MAME's `emu.item()` save-state mechanism (`trace.lua` extended with `NMKTRACE_ITEM_INDEX`), and the RTL's own internal `sprite_snap` buffer was exposed through a new debug readback port threaded from `video_bjtwin.sv` up through `bjtwin_core.sv`'s top-level and read out per-frame by the testbench. This closes out the last of the three internal-state verification gaps (CPU/mainram, tilemap VRAM, sprite DMA buffer).

**The render architecture is now real-time/scanline-synchronized**, replacing the earlier unbounded procedural per-frame FSM (which was never going to be synthesizable as final hardware). Checking MAME's source confirmed it never models a tile-fetch bandwidth limit for this family (only sprites have a real per-frame clock budget), so tile decode became a pure per-pixel combinational function driven the same way a real hardware raster fetcher would run off live `hcount`/`vcount` — which also fixed a genuine wraparound bug (the old sweep left most of the screen with stale/undefined pixels for `scroll_y_reg` values past ~32, never exercised by the captured trace). Sprites, which *do* have a real budget, got a double-buffered plane instead: the same MAME-verified budget-walked draw pass now fills whichever buffer isn't currently displayed, swapping atomically on completion so a redraw in progress can never tear the displayed frame. `frame_done` moved to `bjtwin_core.sv`, tied directly to the real raster counter instead of FSM completion — confirmed to now land exactly 177,920 CPU cycles apart, matching the testbench's independently-derived frame period exactly. Re-running the full sprite_dma() buffer comparison after the rework: **still an exact match, all 16 frames, and the earlier one-frame counting offset is now gone entirely** (a direct consequence of `frame_done` tracking real raster time). The boot-time uniform-color frame from the earlier "End-to-end sanity check" also reproduces identically through the new combinational tile path. Frame-level pixel rendering is still not compared against MAME pixel-for-pixel beyond that one hand-checked case — the underlying state is trusted, but real gameplay content needs to be reachable first (audio, `nmk112`, jt6295x2 are still unverified/stubbed). Full detail in `docs/tier1-bjtwin.md`'s "Real-time scanline-synchronized render architecture" section. An initial ROM-completeness concern about `cactus.zip` turned out to be a false alarm (MAME's split-romset parent merging) — see `docs/rom-audit.md` for the full project-wide audit: **all 101 romsets now verify complete** (`macrossbl` was missing on the first pass, since supplied and reverified good).

Built in three verified passes: the base opcode table (17 instructions matching MAME's own CPU core exactly), then all six "(gg)"/"(mn)"/"($FF00+n)" prefixed groups (86 matching, register-indirect and direct-address forms extended to every register via a second decode level), then the `(ix+d)`/`(iy+d)`/`(HL+A)` indexed groups plus a previously-unidentified register-to-register group (`0xf8-0xfe` — traced there only by following the actual divergence opcode bytes back to the reference source, since it wasn't in the original addressing-mode inventory at all; turned out to be where plain `ADD A,r`-style forms and a second `RET cc` encoding live). **175 real instructions now match MAME's own CPU core exactly**, reaching all the way to the point where the NMK004 boot firmware legitimately blocks polling a host-handshake register only the real 68000 would ever write — confirmed to be a genuine boundary of CPU-only verification (the RTL's own polling loop matches the oracle's exactly), not a bug, and not passable without a fuller system simulation. Along the way, found and fixed a real, reproducible Verilator simulation bug (a helper function silently returned 0 instead of the correct register value when called from inside a specific ternary/non-blocking-assignment composition) and a real correctness gap the new register-to-register group exposed (the `ADD HL,rr` flag special-case, previously dead code since nothing reachable could trigger it). **A real peripheral/timer/interrupt module is now built** (`rtl/tlcs90/nmk004_periph.sv`: ports, timers 0-5 with true compare-match/prescale/chaining behavior matching MAME's `t90_timer_callback`, INTEL/INTEH) and wired into a full board wrapper (`rtl/tlcs90/nmk004_core.sv`) plus real interrupt dispatch added to the CPU core itself (priority-scanned maskable IRQs + NMI, push PC then AF, vector jump, RETI return). Two real bugs found and fixed during bring-up, both confirmed against the oracle: `irq_req` had been left tied to 0 (the timer interrupt that triggers the whole protection mechanism could never fire); `ix_bank`/`iy_bank` had been left unconnected (bank-extended addressing silently stranded at bank 0 regardless of firmware). The game itself still doesn't render: tdragon1's own protection self-test computes a scanline-event count that determines a jump address it patches into 68000 RAM, and that count depends on how many scanline-boundary events have accumulated since reset — which in turn depends on the raster phase at the moment CPU reset releases, relative to video timing. `rtl/bjtwin/video_timing.sv` (shared, unchanged since Tier 1) always resets to `hcount=vcount=0`, a fully deterministic phase that most likely differs from MAME's own reset-relative phase; every prior port's own polling loops were tolerant of this and it only ever showed up as a bounded, already-documented residual-mismatch count in verification — tdragon1 is the first game whose firmware breaks outright on it. Root-caused via extensive MAME-oracle disassembly (traced the self-modifying-trampoline mechanism, the table-select index, and the accumulator down to the exact instruction), not merely observed. Full detail in `docs/tier2-system.md`'s "tdragon1 — Family D, the first TLCS-90 protection-MCU game". **The `video_timing.sv` reset-phase fix was then made and verified in a later session**: `vcount` now resets to `VACTIVE_END` (240, the top of vblank) instead of 0, matching real MAME's own screen-device reset-relative raster phase — confirmed necessary but not sufficient (fixed the raster-phase divergence exactly as diagnosed, zero regressions across all 11 Tier 1/2 ports, one measurable improvement on hachamf, but tdragon1/hachamf still didn't render). **The real remaining root cause was then found and fixed: `tlcs90.sv`'s own opcode decode table was missing six distinct instruction forms**, all silently executing as `OP_NOP` — `ADD ix,mn` (the base-level table-scan-loop advance that was corrupting the self-modifying trampoline patch, confirmed directly against the reference and the actual cause of the divergence traced above) plus five more found via a full ROM byte-pattern scan once the same pattern was suspected again (`MUL/DIV HL,n`/`HL,(mem)`, `ADD ix,gg`/`ix,(mem)`, `LDW ($FF00+w),mn`/`LDW (mem),mn`) — the first ROM in the project's history to exercise any of them. Full regression sweep across all nine ports sharing `tlcs90.sv` with tdragon1/hachamf (mustang, bioship, blkheart, strahl, acrobatm, tdragon, vandyke, hachamfb, hachamf) found zero regressions. Full detail in `docs/tier2-system.md`'s "tdragon1/hachamf — the real root cause: `tlcs90.sv`'s opcode table was incomplete".

Full detail in `docs/tier2-system.md`'s "hachamf — Family D, second TLCS-90 protection-MCU game, same root cause confirmed". **Re-checked after the video_timing.sv and `tlcs90.sv` opcode fixes described above: hachamf is fixed too**, confirmed after an initial false alarm — VRAM/pixel numbers (`palette=478/1024 bgvram=8192/8192 txvram=1024/1024`, `86016/86016` nonzero) first looked like tdragon1's own pre-fix "never cleared" signature, but running the identical check against `hachamfb` (the already oracle-verified unprotected sibling sharing hachamf's exact video architecture) produces the **exact same numbers**, and a rendered PPM frame dump shows a stable, correct "HACHA MECHA FIGHTER" title screen — the same one `docs/PLAN.md`'s own hachamfb entry above already documents.
